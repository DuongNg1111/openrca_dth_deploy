# OUTPUT Module — Owner @thanhthanh278

## Overview

The Output Module is responsible for transforming validated telemetry evidence and RCA results into structured, persistent, and visualization-ready outputs.

In the full RCA pipeline, the Output Module starts from **Step 17** and covers **Steps 17–22**.

```text
PROCESS MODULE
Steps 9–16
    │
    │ Validated / correlated / localized evidence
    ▼
OUTPUT MODULE
Steps 17–22
    │
    ├── Step 17: Prepare Context & Evidence
    │       │
    │       └── Evidence Validation Checklist
    │
    ├── Step 18: Reasoning Agent
    │       │
    │       └── RCA Result
    │
    ├── Step 19: Process RCA Result
    │
    ├── Step 20: Save RCA Result
    │       │
    │       └── PostgreSQL
    │
    ├── Step 21: RCA Output
    │
    └── Step 22: Demo
            │
            ▼
      Streamlit / My Incidents
```

The Output Module focuses on **evidence preparation, reasoning orchestration, RCA result processing, persistence, visualization, and presentation**.

The actual root cause inference is performed by the **Reasoning Agent**, while the Output Module prepares the required context/evidence and handles the resulting RCA output.

---

# Pipeline Responsibilities

## Step 17 — Prepare Context & Evidence

Step 17 prepares the evidence collected by the Process Module for the reasoning stage.

The module receives evidence from:

* Metric Agent
* Log Agent
* Trace Agent

The evidence is organized into a consistent context before being passed to the Reasoning Agent.

### Evidence Validation Checklist

The Output Module includes `checklist.py` to validate whether the collected evidence is suitable for reasoning.

The checklist is used to verify:

* Evidence availability
* Evidence sufficiency
* Evidence validity
* Evidence consistency
* Service/context consistency
* Supporting evidence
* Conflicting evidence
* Reasoning readiness

The checklist helps prevent the Reasoning Agent from producing conclusions when the available evidence is insufficient or contradictory.

```text
Evidence
   │
   ▼
Evidence Validation Checklist
   │
   ├── Sufficient?
   ├── Valid?
   ├── Consistent?
   ├── Conflicting?
   └── Ready for reasoning?
   │
   ▼
Reasoning Agent
```

---

# Step 18 — Reasoning Agent

After the evidence has been prepared and validated, the RCA context is passed to the Reasoning Agent.

The Reasoning Agent combines evidence from multiple telemetry sources and uses an LLM to generate the RCA result.

Typical inputs include:

* Affected services
* Metric evidence
* Log evidence
* Trace evidence
* Baseline information
* Anomaly information
* Evidence relationships
* Evidence validation results

The Reasoning Agent produces structured RCA information such as:

* Root Cause
* Supporting Evidence
* Confidence Score
* Affected Component
* Explanation
* Recommended Actions

### Reasoning Rules

The reasoning process follows a predefined set of reasoning rules to keep RCA conclusions grounded in the available evidence.

The rules are designed to:

* Avoid unsupported conclusions.
* Use supplied telemetry evidence.
* Check relationships between evidence sources.
* Handle missing evidence.
* Detect conflicting evidence.
* Consider metric, log, and trace consistency.
* Calculate or assign confidence based on evidence strength.
* Produce structured RCA output.

The reasoning stage should not introduce facts that cannot be supported by the available telemetry evidence.

---

# Step 19 — Process RCA Result

After the Reasoning Agent generates the RCA result, the Output Module processes the result into a standardized structure.

This stage is responsible for:

* Normalizing RCA fields.
* Organizing root cause information.
* Preserving supporting evidence.
* Preserving confidence information.
* Preparing the result for persistence.
* Preparing the result for downstream visualization.

The output should preserve the conclusion generated by the Reasoning Agent without introducing unrelated reasoning.

---

# Step 20 — Save RCA Result

The processed RCA result is persisted in PostgreSQL.

The database allows RCA results to be retrieved later by the dashboard and other downstream components.

Typical persisted information includes:

* Investigation ID
* Affected service
* Root cause
* Confidence
* Supporting evidence
* Recommended actions
* RCA metadata

```text
Reasoning Agent
      │
      ▼
RCA Result
      │
      ▼
Formatter / Processing
      │
      ▼
PostgreSQL
```

This separates RCA generation from RCA presentation and allows the Streamlit application to retrieve results independently.

---

# Step 21 — RCA Output

The stored RCA result is transformed into dashboard-ready information.

The Output Module prepares information such as:

* Incident summary
* Root cause
* Confidence
* Key findings
* Metric abnormalities
* Log evidence
* Trace evidence
* Supporting evidence
* Incident timeline
* Recommended actions

The Streamlit application is responsible for rendering the final user interface.

# Design Principles

## 1. Evidence-Grounded Reasoning

RCA conclusions should be based on the evidence provided by the telemetry pipeline.

The Reasoning Agent should not introduce unsupported facts.

## 2. Evidence Validation Before Reasoning

Evidence should pass the Step 17 validation/checklist stage before being used for RCA reasoning.

## 3. Separation of Reasoning and Presentation

The Reasoning Agent generates the RCA conclusion.

The Output Module processes, stores, and prepares the result for presentation.

Streamlit is responsible for rendering the final UI.

## 4. Persistent RCA Results

RCA results should be stored in PostgreSQL so that they can be retrieved independently of the pipeline execution.

## 5. Standardized Output

RCA results should use consistent structures so they can be consumed by:

* Streamlit
* OpenRCA-compatible workflows
* Reports
* Visualization components
* Future downstream applications
